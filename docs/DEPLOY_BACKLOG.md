## Закономерность

- Успехи и провалы чередуются без изменений кода/секретов/workflow → проблема не в конфигурации, а в соединении GitHub Actions ↔ Timeweb.
- Характер ошибки: `ssh: connect to host *** port 22: Operation timed out` (не «connection refused») — пакеты теряются или фильтруются.
- Серии таймаутов длятся десятки минут, затем соединение восстанавливается само.

## ОТВЕТ ПОДДЕРЖКИ TIMEWEB (2026-08, закрывает расследование)

1. Блокировок Azure/GitHub Actions нет, whitelist добавить не могут.
2. SSH работает на стандартном 22 порту, GeoIP-фильтрации нет.
3. Rate-limit есть как общий защитный механизм сервера.
4. **Корневая причина серий таймаутов: DDoS-атака на сервер 11–12 августа** — совпадает с нашими инцидентами (09:13, 11:55 и далее). При отражении атаки возможны кратковременные потери пакетов для легитимных подключений — это объясняет серийный временный характер сбоев.
5. Если таймауты повторятся ВНЕ периодов таких инцидентов: прислать им **конкретный IP раннера + точное время (до секунды)** неудачной попытки — проверят прохождение пакета адресно.

### Как снять IP раннера и точное время при следующем инциденте

В логе failed-шага `Deploy via SSH` GitHub указывает время каждой строки (ISO8601 с мс). IP раннера можно получить, добавив в workflow диагностический шаг `curl -s ifconfig.me` (только при failure) — внедрить при следующем изменении `.github/workflows/preview.yml` с отдельного одобрения.

## Возможные причины (по вероятности)

1. **fail2ban / CSF / rate-limit на Timeweb**: серия rsync-подключений с разных IP GitHub Actions (Azure) выглядит как перебор → временный бан подсетей. Объясняет «само прошло» через ~30–60 минут.
2. **GeoIP/сетевой фильтр хостинга** на SSH для зарубежных диапазонов (GitHub runners — Azure, чаще не-RU).
3. **Маршрутизация/потери** между Azure и сетью Таймвеба в часы нагрузки.
4. Нестабильность sshd/сети самого shared-сервера.

## Действия при повторении

1. Проверить последний run: `gh run list --branch feat/home-design-system --limit 1`.
2. При failure — `gh run rerun <id>` (секреты и код не трогать).
3. Серия из 3+ failure подряд → отправить письмо выше, деплой подождёт восстановления SSH.
4. Cron-ретрай (сессия Kimi): каждые 23 минуты, авто-стоп при success или после 6 попыток.
